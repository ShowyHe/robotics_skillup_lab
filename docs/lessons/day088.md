# Part A — Foundation（基础层）

## 1. Reuse Review：Path、Trajectory 与 Reference

Day80 已经建立：

- **Geometric Path（几何路径）**：描述机器人应该经过哪些空间位置，不直接规定到达时间。
- **Timed Trajectory（时间参数化轨迹）**：规定位置等状态随时间如何变化。
- **Reference（参考量）**：控制器在当前时刻希望机器人达到的目标状态或输出。

几何路径：

\[
P(s)=\begin{bmatrix}x(s)\\y(s)\end{bmatrix}
\]

时间参数化：

\[
p_r(t)=P(s(t)),\qquad v_r(t)=\frac{dp_r(t)}{dt}
\]

同一条几何路径可以对应不同速度曲线和到达时间。只知道 Path，不等于知道每个时刻应该达到什么状态。

## 2. Tracking Problem：跟踪问题的基本对象

先考虑平面移动机器人，世界坐标系为 \(W\)，机器人本体坐标系为 \(B\)。

实际状态：

\[
x=\begin{bmatrix}x&y&\theta&v&\omega\end{bmatrix}^{T}
\]

参考状态：

\[
x_r=\begin{bmatrix}x_r&y_r&\theta_r&v_r&\omega_r\end{bmatrix}^{T}
\]

其中位置单位 m，航向单位 rad，线速度单位 m/s，角速度单位 rad/s。Tracking 不只是位置靠近路径，还涉及航向和速度是否跟上参考。

## 3. Error Convention：误差坐标与正负号

本讲义约定：

- 世界坐标系为右手平面坐标系，\(\theta\) 从世界系 \(+x_W\) 轴转向机器人前向轴，逆时针为正；实际系统按 map / odom 的真实定义核对；
- 机器人本体坐标系 \(x_B\) 向前、\(y_B\) 向左；
- 位置误差定义为“参考减实际”；
- 航向误差定义为参考航向减实际航向，并 wrap 到 \((-\pi,\pi]\)。

误差正负号取决于坐标系和实现约定。不同代码可能采用相反符号，不能脱离约定比较。

## 4. Lateral Error：横向误差

世界坐标系位置差：

\[
\Delta p^W=\begin{bmatrix}x_r-x\\y_r-y\end{bmatrix}
\]

旋转到机器人本体坐标系：

\[
e_p^B=R(\theta)^T\Delta p^W,\quad
R(\theta)=
\begin{bmatrix}
\cos\theta&-\sin\theta\\
\sin\theta&\cos\theta
\end{bmatrix}
\]

横向误差：

\[
\boxed{e_y=-\sin\theta(x_r-x)+\cos\theta(y_r-y)}
\]

单位 m。在本讲义约定下，正值表示参考位置位于机器人左侧。横向误差回答机器人相对参考轨迹横向偏了多少。

## 5. Heading Error：航向误差

\[
\boxed{e_\theta=\operatorname{wrap}(\theta_r-\theta)}
\]

单位 rad。按本讲义约定，正值表示需要向左增加航向，负值表示需要向右修正。若系统采用不同 yaw 正方向、ENU/NED 或角度 wrap 约定，必须重新核对。

位置可能已经在路径上但航向不对；也可能航向正确却横向偏离路径。二者不是同一个误差。

## 6. Velocity Error：速度误差

线速度误差：

\[
\boxed{e_v=v_r-v_{\mathrm{actual}}}
\]

角速度误差：

\[
\boxed{e_\omega=\omega_r-\omega_{\mathrm{actual}}}
\]

单位分别为 m/s、rad/s。这里的 actual 必须来自实际反馈或明确的状态估计，不能直接把上一次发布的 cmd_vel 当作真实速度。

## 7. Reference、Command、Feedback、Actual Motion

| 对象 | 含义 | 能否证明机器人实际达到 |
|---|---|---|
| Reference / Setpoint | 控制器希望达到的目标 | 不能 |
| Controller Command | 控制器输出的命令 | 不能 |
| Base Accepted Command | 下游或底盘实际接收的命令 | 仍不能 |
| Actual Feedback / Motion | 编码器、IMU、里程计等反映的运动估计 | 是判断实际运动的主要依据，但仍有测量误差 |

例如 \(v_{\mathrm{cmd}}=0.8\,m/s\)，不意味着 \(v_{\mathrm{actual}}=0.8\,m/s\)。命令可能被限幅、平滑、急停、安全层覆盖，或底盘能力不足。

## 8. Latency、Age、Jitter

- **Latency（延迟）**：数据或动作从起点到终点经历的时间。
- **Age（年龄）**：当前使用的数据，距离它所代表的实际状态时刻已经过去多久。
- **Jitter（抖动）**：延迟或周期随时间变化的程度。

控制器每 50ms 更新一次，但读到的状态代表 400ms 以前的机器人状态时，控制周期是 50ms，状态年龄是 400ms。二者不是同一个量。

## 9. Timestamp Chain：控制链的时间戳

建议区分：

| 时间戳 | 含义 |
|---|---|
| \(t_{\mathrm{sensor}}\) | 传感器采集时刻 |
| \(t_{\mathrm{estimate}}\) | 状态估计所代表的状态时刻 |
| \(t_{\mathrm{estimate\_pub}}\) | 状态估计发布时刻 |
| \(t_{\mathrm{control}}\) | 控制器读取并计算时刻 |
| \(t_{\mathrm{cmd}}\) | 控制命令发布时刻 |
| \(t_{\mathrm{base}}\) | 底盘接收命令时刻 |
| \(t_{\mathrm{feedback}}\) | 实际反馈所代表的状态时刻 |

必须区分消息什么时候发布和消息代表机器人什么时候的状态。估计器在 400ms 后才发布一条旧状态，只看 publish timestamp 可能误以为数据很新。

参与相减的时间戳必须处于可比较的时钟域，并考虑时钟同步误差。

## 10. State Age：状态年龄

控制器读取状态时刻为 \(t_c\)，状态所代表的时刻为 \(t_s\)：

\[
\boxed{A_{\mathrm{state}}=t_c-t_s}
\]

单位 s。如果状态代表 400ms 前的机器人，则 State Age 为 0.4s。

若估计器把旧测量向前预测到当前，状态时间戳可能接近当前，但底层测量仍可能很旧，因此还要单独记录：

\[
A_{\mathrm{measurement}}=t_c-t_{\mathrm{sensor}}
\]

**State Age 与 Measurement Age 不一定相等。** 必须知道时间戳具体代表什么。

## 11. Controller Frequency ≠ Feedback Freshness

\[
f_c=\frac{1}{T_c}
\]

20Hz 对应：

\[
T_c=0.05s
\]

20Hz 只说明控制器每 50ms 触发一次计算，不证明状态估计每 50ms 更新、时间戳最新、传感器没有排队、TF 对应正确时刻，或底盘每 50ms 都能接收并执行命令。

控制频率、状态发布频率、状态年龄和端到端延迟必须分别测量。

# Part B — Core Theory（核心理论层）

## 12. Delayed Feedback：延迟反馈

无明显延迟时：

\[
u(t)=\pi(x_r(t)-\hat x(t))
\]

状态滞后 \(T_d\) 时：

\[
\boxed{u(t)=\pi(x_r(t)-\hat x(t-T_d))}
\]

控制器实际使用的是过去的状态估计。机器人在 \(T_d\) 内已经继续运动，但控制器还在根据过去的偏差纠正。如果参考和反馈没有按同一时间基准对齐，还会额外引入时间错配。

## 13. 20Hz + 400ms：定量理解

已知控制频率 20Hz、周期 50ms、状态年龄 400ms：

\[
N_d=\frac{0.4}{0.05}=8
\]

当前控制器使用的状态大约落后 8 个控制周期。

这不等于控制器只运行了 12.5Hz，也不必然表示同一条消息重复了 8 次；它表示反馈所代表的物理时刻比当前控制时刻落后 400ms。

## 14. 旧状态对应的空间差距

仅作恒速估算：假设机器人在 400ms 内线速度保持 \(0.8m/s\)，不考虑转弯和外部扰动：

\[
d=vT=0.8\times0.4=0.32m
\]

若角速度保持 \(0.5rad/s\)：

\[
\Delta\theta=\omega T=0.5\times0.4=0.2rad\approx11.46^\circ
\]

因此旧状态与当前真实状态之间可能已经存在明显空间差异。这是恒速、恒角速度假设下的估算，不是任意机器人 400ms 延迟的固定误差。

## 15. Delay-induced Oscillation：延迟为何可能造成 S 形摆动

以路径跟踪为例：

1. 机器人已经向路径右侧偏移；
2. 控制器根据旧状态，仍认为机器人处于更早的位置；
3. 控制器继续输出向左修正；
4. 机器人已经接近路径中心，甚至越过中心；
5. 新反馈到达时，控制器才发现偏差已经换边；
6. 控制器开始向右修正，但该修正也经过执行器和反馈延迟；
7. 机器人可能再次越过路径中心。

形成左右交替修正，表现为 S 形摆动：

\[
\boxed{
旧状态\rightarrow错误时刻的纠偏
\rightarrow过度修正\rightarrow反向纠偏\rightarrow振荡
}
\]

这是可能的因果链，不是所有 S 形摆动的唯一原因。模型失配、轮速反馈错误、角速度比例错误、执行器滞后、控制增益过高也可能产生相似现象。

## 16. Actuator Dynamics：执行器不是理想速度发生器

控制器输出速度命令，不代表底盘能瞬间达到该速度。一个常见的一阶执行器近似：

\[
\boxed{\tau_a\dot v_a+v_a=v_{\mathrm{cmd}}}
\]

其中 \(v_{\mathrm{cmd}}\)、\(v_a\) 单位 m/s，\(\dot v_a\) 单位 m/s²，时间常数 \(\tau_a\) 单位 s。

这是连续时间、单轴、线性、一阶近似。真实底盘可能存在死区、非线性、饱和、方向差异和额外纯延迟。

## 17. 一阶响应：命令变化后速度仍需要时间

若命令阶跃到常数 \(v_{\mathrm{cmd}}\)，且忽略饱和：

\[
v_a(t)=v_{\mathrm{cmd}}+
(v_a(0)-v_{\mathrm{cmd}})e^{-t/\tau_a}
\]

当 \(t=\tau_a\) 时，实际速度完成总变化量的约 63.2%。

例如初始速度 0、命令 1m/s、时间常数 0.2s：

\[
v_a(0.2)=1-e^{-1}\approx0.632m/s
\]

命令已经是 1m/s，实际速度仍不一定达到 1m/s。

## 18. Pure Delay 与 Actuator Lag

**纯延迟（Pure Delay）：**

\[
v_a(t)=v_{\mathrm{cmd}}(t-T_d)
\]

命令经过一段时间后才开始体现。

**一阶滞后（First-order Lag）：**

\[
\tau_a\dot v_a+v_a=v_{\mathrm{cmd}}
\]

命令已经开始影响系统，但实际速度逐渐接近目标。

实际机器人可能同时存在两者：

\[
\tau_a\dot v_a(t)+v_a(t)
=u_{\mathrm{effective}}(t-T_d)
\]

不能只用“响应慢”概括全部问题。

## 19. Velocity Saturation：速度幅值饱和

控制器希望输出 \(0.8m/s\)，但下游最大允许速度为 \(0.5m/s\)，实际接受的命令可能是：

\[
\boxed{
v_{\mathrm{effective}}
=\operatorname{clip}(v_{\mathrm{cmd}},v_{\min},v_{\max})
}
\]

若预测模型仍按 0.8m/s rollout，预测运动与真实运动会产生系统性差异。

需要分别检查 MPPI 自身、速度平滑器、底盘固件 / 驱动器以及电机和机械系统的速度边界。

## 20. Acceleration / Rate Saturation：加速度与变化率限制

即使目标速度没有超过最大速度，也可能因为加速度限制无法立即达到：

\[
\boxed{|v_k-v_{k-1}|\le a_{\max}\Delta t}
\]

例如 \(a_{\max}=0.5m/s^2\)、\(\Delta t=0.05s\)：

\[
\Delta v_{\max}=0.5\times0.05=0.025m/s
\]

每个 50ms 周期最多变化 0.025m/s。角速度也可能有独立角加速度限制：

\[
|\omega_k-\omega_{k-1}|\le\alpha_{\max}\Delta t
\]

速度幅值限制与加速度限制是两种不同约束。

## 21. Command Saturation 与 Physical Saturation

必须区分：

- **Software clipping**：软件主动裁剪命令；
- **Controller rate limiting**：按加速度 / 变化率限制命令；
- **Motor / Driver saturation**：驱动器或电机达到输出能力边界；
- **Mechanical / Traction limitation**：轮胎打滑、地面摩擦、负载或坡度导致无法实现期望运动。

只记录 MPPI 输出，不记录下游节点和底盘实际接收值，就无法知道速度在哪一层发生变化。

## 22. Model Mismatch：模型失配

模型失配是控制器用于预测的模型与真实系统状态转移规律存在差异。

预测模型：

\[
\hat x_{k+1}=f_{\mathrm{model}}(\hat x_k,u_k,\Delta t)
\]

真实系统：

\[
x_{k+1}=f_{\mathrm{real}}(x_k,u_{\mathrm{actual}},\Delta t)+w_k
\]

其中 \(u_k\) 是控制器输入，\(u_{\mathrm{actual}}\) 是底盘实际执行的输入，\(w_k\) 表示外部扰动和未建模影响。

模型失配不一定是公式写错，也可能是控制器给出的输入没有被真实底盘执行。

## 23. Prediction Residual：预测与实际的差值

在相同时间、相同坐标系下比较：

\[
\boxed{
r_{k+1}=x_{\mathrm{actual}}(t_{k+1})
-x_{\mathrm{predicted}}(t_{k+1})
}
\]

yaw 误差需要使用角度 wrap，不能直接对跨越 \(\pm\pi\) 的角度做普通减法。

比较之前必须保证：
1. 预测和实际状态对应同一时刻；
2. 使用同一个坐标系和参考原点；
3. 起始状态一致；
4. 使用底盘实际接受的输入，或明确记录命令与实际输入差异；
5. \(\Delta t\) 一致。

若拿 400ms 前的预测状态和当前实际位姿直接相减，差值包含时间推进，不是纯粹的模型失配。

## 24. Model Mismatch 的常见来源与归因边界

| 来源 | 可能表现 | 先检查什么 |
|---|---|---|
| 轮半径 / 轮距参数 | 线速度或转向预测比例不符 | 轮速积分与实测位姿 |
| 电机 / 底盘响应 | 命令变化后实际速度跟不上 | 命令、底盘接收、轮速反馈 |
| 加速度限制 | 预测加速快于实际加速 | 限幅前后速度及实际加速度 |
| 时间戳 / model_dt | 预测和反馈不在同一时间 | 状态时间、控制周期、模型步长 |
| 轮胎打滑 / 地面变化 | 相同轮速对应不同位移 | 轮速、IMU、外部定位对照 |
| 初始状态错误 | 每条预测轨迹起点就不正确 | 当前位姿、速度来源和时间戳 |
| 外部扰动 | 运动偏离模型预测 | 地面、碰撞、外力及载荷变化 |

看到预测残差大，不能立即断言模型公式错误。必须先排除时间错配、起始状态不一致和实际输入不一致。

## 25. Smoothing Trade-off：平滑与响应速度的权衡

速度平滑器可以限制速度幅值、加速度 / 减速度、速度死区，并在控制器频率较低时插值输出更平滑的命令。

但平滑也可能使速度变化更慢、转向命令滞后；下游限幅会改变 MPPI 的预测结果；闭环平滑器若使用过时里程计，可能增加延迟甚至振荡。

因此平滑不是越强越好，要在机械可执行性、舒适性和跟踪响应之间权衡。

## 26. Nav2 Humble Velocity Smoother：具体机制

根据 Nav2 Humble Velocity Smoother 文档与源码：

1. 输入控制器的速度命令；
2. 以独立 timer 周期运行；
3. 对速度幅值、加速度 / 减速度和 deadband 做限制；
4. 输出平滑后的速度命令；
5. 支持 OPEN_LOOP 和 CLOSED_LOOP 两种反馈方式。

**OPEN_LOOP：** 使用上一条平滑输出作为当前速度估计。

**CLOSED_LOOP：** 从 odometry 读取当前速度，再计算可达到的速度变化。

Nav2 文档举例：Controller 以 20Hz 运行时，Velocity Smoother 可以以 100Hz 输出更细的速度插值。

官方文档还提醒：闭环模式中，如果 smoother 频率高于 odometry 频率，或 odom_duration 选择不当，机器人可能振荡或加速缓慢。因此不能只看 smoother_frequency，还要同时检查 odometry 频率、延迟和数据新鲜度。

## 27. Safety Override：安全层可以覆盖正常控制命令

控制器给出正常命令后，系统可能还有独立安全层对命令进行过滤或覆盖。

Nav2 Humble Collision Monitor 位于 Nav2 控制器下游，作为独立节点处理速度命令。其行为模型包括：

- STOP：输出零速度；
- SLOWDOWN：按比例降低速度；
- APPROACH：根据预计碰撞时间降低速度。

它可以使用 LaserScan、PointCloud 或 Range 等数据源，并按配置区域 / footprint 处理。

因此最终命令应区分：

\[
u_{\mathrm{controller}}
\rightarrow
\{\text{configured smoother / safety layers in actual order}\}
\rightarrow u_{\mathrm{base}}
\]

不能看到底盘实际速度为零，就直接断言 MPPI 输出了零。

软件安全覆盖依赖传感器、时间戳、TF、配置和节点运行状态；不能把它等同于独立硬件急停，也不能仅凭配置宣称达到功能安全认证。

# Part C — Advanced / Owner（进阶 / Owner 层）

## 28. Prediction vs Actual：建立同一时间轴

判断 MPPI 模型是否预测正确，必须把预测状态与实际反馈放到同一时间轴。

| 时刻 | 预测 / 命令 | 实际反馈 |
|---|---|---|
| \(t_0\) | 初始预测位姿、速度 | 同一时刻的状态估计 |
| \(t_1\) | 第一步预测速度和位姿 | 轮速 / IMU / Odom |
| \(t_2\) | 后续预测状态 | 对应时刻的实际状态 |
| \(t_3\) | 预测终点 | 对齐后的实际终点 |

不要把预测的未来 1 秒状态、400ms 前的 LIO 位姿和当前轮速反馈直接混在一起做差。先完成时间对齐，再计算位置、航向和速度残差。

## 29. S-shaped Oscillation：快速排查顺序

出现 S 形摆动时，先定位命令在哪一层开始与预期不一致，不要一开始同时调 MPPI、PID、smoother 参数。

建议优先顺序：

1. **State Freshness：** 当前控制器使用的位姿、速度是否新鲜？timestamp 和 State Age 是否正确？
2. **Actual Feedback：** 轮速、IMU、Odom 是否反映真实运动？是否把旧命令当作实际速度？
3. **Command Chain：** MPPI 输出是否被 smoother、safety override、底盘限幅改变？
4. **Actuator Response：** 底盘接收命令后，实际速度是否按预期建立？加速度和制动能力如何？
5. **Model Consistency：** 时间对齐后，预测与实际是否仍持续存在同方向、同规律的残差？
6. **Controller / Cost：** 前面各层证据正常后，再检查预测模型、控制增益、Critic 和轨迹选择。

这是快速责任归因顺序，不意味着所有问题都必须把六项日志完整分析一遍。前一层已明确发现错误时，优先修复并复测。

## 30. Owner Evidence Chain：最小证据集与判断

| 阶段 | 最小证据 |
|---|---|
| Reference | 当前参考位置、航向、速度及参考时间 |
| State | 位姿、速度、frame、state timestamp |
| Freshness | State Age、measurement age、接收时间 |
| Prediction | 初始状态、model_dt、预测位姿 / 速度 |
| Controller | MPPI 输出 cmd_vel |
| Smoother | 平滑前后命令及限幅原因 |
| Safety | STOP / SLOWDOWN / APPROACH 等覆盖动作及原因 |
| Base | 底盘接收命令、使能状态 |
| Actual | 轮速、IMU、Odom / 定位反馈及时间戳 |
| Residual | 同一时间、同一 frame 下的预测—实际误差 |

排查原则：

- 命令在 Controller 输出时就不合理：先查状态、参考、模型和优化结果。
- Controller 命令合理，但下游命令改变：查 smoother、safety override 或限幅。
- 底盘接收命令合理，但实际速度不跟随：查底盘使能、驱动器、执行器和运动学参数。
- 预测与实际在时间、frame、输入对齐后仍持续偏离：才进一步确认模型失配。
- 状态本身滞后或错误：不能用调大控制增益来补偿错误反馈。

## Q4 — Actuator Dynamics（计算 / Hard Gate）

\[
\tau_a\dot v_a+v_a=v_{\mathrm{cmd}}
\]

计算 0.2s 时的实际速度，并解释时间常数的物理意义。

## Q5 — Velocity / Acceleration Saturation

控制器以 50ms 周期运行，加速度上限 0.5m/s²。

3. 为什么 MPPI 输出 0.8m/s，底盘实际可能只有 0.5m/s？

## Q6 — Model Mismatch（Hard Gate）

写出预测状态与实际状态的残差定义。比较之前必须保证哪些条件一致？至少给出四项。

## Q7 — Delay-induced Oscillation

## Q8 — Smoothing Trade-off

Velocity Smoother 的作用是什么？OPEN_LOOP 和 CLOSED_LOOP 反馈分别使用什么信息？为什么 CLOSED_LOOP 在 odometry 低频或滞后时可能引起振荡？

## Q9 — Safety Override

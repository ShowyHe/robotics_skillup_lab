## 1. 今日目标与职责链

区分 Nav2 中 BT Navigator、Planner Server、Controller Server、Recovery 的职责，理解 Keep/Switch/Replan 各在什么条件下成立。

~~~text
Goal / NavigateToPose Action
            ↓
       BT Navigator
       ├─ Planner Server → Global Path
       ├─ Controller Server ← Path → cmd_vel
       ├─ Recovery / Retry / Clear Costmap ...
       └─ Replan / Path Switch policy (BT or related logic)
            ↓
      Robot + Feedback / Result
~~~

这是**职责图而不是所有 Nav2 BT 的固定执行顺序**：BT 可循环 Tick、重算路径、发不同 Action，不是一条只执行一次的线性流水线。

## A. Foundation（01–08）

### 01. ROS 2 Action 的最小语义

Action 适合持续一段时间的任务，包含：
- Goal：请求执行什么，例如 NavigateToPose、ComputePathToPose、FollowPath；
- Feedback：执行中的阶段/进度/剩余距离等，具体字段取决于 Action；
- Result：任务结束返回结果或错误；
- Cancel：尝试取消尚未结束的目标。

**“Action Goal 已接收”不等于“导航成功”；执行成功与否要结合状态和结果判断。**

### 02. Planner Server

根据地图/代价图、机器人起点、目标及插件规划参数计算 Global Path。它负责**提供路径**，不负责直接输出持续的底盘速度。路径结果的合理性取决于规划模型、碰撞校验与数据新鲜度。

### 03. Controller Server

接收/使用路径和机器人状态，计算控制指令（常见为 \(\mathrm{cmd\_vel}\)）；它解决沿路径的实时跟踪问题，也可能因障碍、进度或安全约束而停止或失败。**Controller 有可行路径不等于底盘能按期望速度真实跟踪。**

### 04. BT Navigator

Behavior Tree（行为树）负责任务级执行顺序、条件选择、重试、重新规划/恢复决策等。BT 节点常见返回状态为 SUCCESS、FAILURE、RUNNING，循环 Tick 时可能重新求值。

### 05. Sequence 与 Fallback

- Sequence：按顺序执行子节点，遇到 FAILURE 停止并返回 FAILURE；遇到 RUNNING 返回 RUNNING；全部成功才 SUCCESS。
- Fallback/Selector：依次尝试子节点，某节点成功即可 SUCCESS；RUNNING 暂停后续尝试；全部失败才 FAILURE。
- 具体是否重启、何时重新 Tick、是否保留先前状态还取决于控制节点类型；不能把上面简化成所有 BT 的完整执行语义。

### 06. Recovery 是行为类别

Recovery 不等于 BackUp。常见恢复动作/策略包括 Spin、BackUp、Clear Costmap、等待、重试等；真正可用的节点取决于 Nav2 版本、机器人运动能力和 BT 配置。Recovery 不应越过碰撞/安全约束强行运动。

### 07. Lifecycle（生命周期）

典型受管节点包含 unconfigured、inactive、active、finalized 等状态。通常先 configure 再 activate，之后服务/动作才能正常工作。出现导航不响应时，应检查节点是否 active、插件加载和接口可用性，而不只怀疑路径算法。

### 08. Goal / Path / Feedback 的边界

Goal 是任务目标；Path 是空间路径建议；Controller 生成速度命令；Feedback 告诉任务/执行过程状态。不能把“有 Path”当作“BT 已完成”，也不能把“Controller 刹停”直接当作“Global Planner 失败”。

## B. Core Theory（09–17）

### 09. 全局路径有效性

路径有效性应根据当前地图/代价图、Footprint、机器人朝向与位姿、碰撞检测范围/时效判断。旧 Path 在原地图上合法，不保证新障碍出现后仍合法；新 Path 算出来也不保证已经通过完整执行可行性检查。

### 10. Periodic / Event-driven Replanning

- Periodic：以固定/配置频率请求新路径；可以适应渐进变化，但增加计算与切换决策负担。
- Event-driven：遭遇确认阻塞、路径失效、偏离严重等事件才触发；需处理传感器噪声、误报和响应延迟。
- 二者可以组合；**触发 Replan 不等于必须 Switch**。

### 11. Keep / Replan / Switch 是三件事

- Keep：旧路径仍可执行，且没有足够收益切换；继续跟踪。
- Replan：重新尝试生成候选路径，是“计算行为”，不是“提交替换”。
- Switch：新路径已经验证，可用且根据策略决定优于保留旧路，才替换跟踪目标。
- Recover：没有可行路径/无法执行时，执行配置允许的恢复动作或上报失败。

### 12. 路径切换比较的是多因素，不只长度

候选路径收益可综合考虑长度/时间、清障裕度、倒退、转向成本、轨迹连续性、对当前位置的重接入代价和控制状态。可设计代价比较：

\[
\mathrm{Switch}\ \text{only if}\ 
C(P_{\mathrm{new}})+C_{\mathrm{switch}}+\Delta
<
C(P_{\mathrm{old}})
\]

其中 \(\Delta>0\) 是阈值/滞回裕度，**只是说明机制的示例**，不是公司代码里的已验证公式或真实阈值。

### 13. Hysteresis / Persistence / Cooldown

- Hysteresis（滞回）：切换需要比旧路径“明显更优”，避免小幅代价波动触发往返切换。
- Persistence（持续性）：故障、障碍或优势要持续到可信条件再做决定，降低单帧噪声影响。
- Cooldown（冷却）：短期限制重复切换频率；必须注意新出现的安全紧急情况不能被冷却机制屏蔽。

### 14. Keep/Switch 决策示例

两条候选路径：旧路 \(P_o\) 当前已经跟踪且无碰撞，新路 \(P_n\) 几何长度稍短，但起点接入要求大幅反转。若新路切换成本高，且长度收益很小，合理策略是 Keep。若新障碍已可靠阻断旧路，并有经验证的新路，则可 Switch；若新路尚未验证，应先 Replan/Verify，不可直接接管。

### 15. Planner Failure 与 Controller Failure

- Planner 未找到有效路：先核起终点、地图/代价图、碰撞有效性、算法和超时。
- 已有有效路径，但控制跟踪无法推进：先核速度命令、反馈、局部障碍、Goal/Progress Checker、底盘响应。
- 反复路径跳变：查重规划触发与 Switch Guard、代价比较、持久化/滞回。
- 上述是**排查入口，不是“一看到某现象就唯一确定归因”**。系统可能同时存在多种故障。

### 16. Recovery 与重新规划的责任界面

障碍出现时，Controller 可以先减速/停止或请求恢复；BT 可以选择继续等待、Clear Costmap、Replan 等。**是否发生恢复、何时执行、触发阈值是什么，以实际 BT XML、插件配置和日志为准。**

### 17. PathSwitchGuard（概念）

切换守卫可检查：新路径碰撞合法性、与当前位姿可接入性、规划时戳、目标一致性、收益阈值、切换频度。它可以是工程决策模块，但**不能假定未读过的仓库里存在同名实现**。

## C. Advanced / Owner（18–22）

### 18. 机器人导航中需要的证据

~~~text
Navigate Goal / BT Tick
   ├─ ComputePathToPose: Goal, start, planner status, path timestamp
   ├─ Path validity: costmap timestamp, Footprint, offending segment
   ├─ FollowPath: controller status, progress, command/feedback
   └─ Switch/Recovery: old/new path IDs, checks, reasons, decisions
~~~

分析时将事件按照**同一时钟、相同 frame 与相同路径版本**对齐，否则可能把前一条路径的控制故障误算成后一条。

### 19. 行人挡路的分层决策

行人短暂阻挡局部路径：先确定是否短期可等待/局部避障。若旧路径在足够长的有效区间内被阻断、局部无法通过，可请求高层重规划；候选新路仍须经过验证并考虑 Switch Cost。不能只依据一个障碍检测帧判定“BT 应该换路”。

### 20. Keep / Switch / Replan 的反例

“新路径更短”不意味着可以立刻切换；“旧路径上出现一个代价点”不意味着整条路径永久失效；“Controller 输出零速度”不自动说明 BT 会终止任务。决定依赖来源、时效、路径持续可用性和任务策略。

### 21. Controller 与底盘边界

Controller 计算 \(\mathrm{cmd\_vel}\)，底盘是否按速度响应需要里程计、轮速/关节状态、通信延迟与安全链验证。规划逻辑正确，也可能在底盘响应或急停链上失败。

### 22. 教学迁移题（新增练习，不属于历史考试）

场景：旧路仍通，新路径短 3% 但需要立即大幅掉头；Planner 已算出新路径。是否必须 Switch？为什么？  
**参考判断：** 不必；先验证新路、比较收益与切换成本，考虑滞回/冷却和执行连续性。若旧路实际上已失效，则判断前提改变。

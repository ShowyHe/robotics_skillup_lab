# 01_plan.md

# 01｜Nav2 架构抽象与执行链重建｜模块计划

## 1. 模块定位

`01_nav2_foundation_7d` 不是基础概念扫盲模块，也不是“把 Nav2 demo 再跑一遍”的重复训练模块。

本模块的定位，是在已经具备 Nav2 运行、评估、bag 回放、failure case 整理与文档沉淀经验的前提下，对 Nav2 做第一次系统级重建。

它要解决的不是下面这类表层问题：

- planner 是干什么的
- controller 是干什么的
- costmap 有哪些参数
- 某个 demo 为什么能跑起来

而是要系统回答以下问题：

- 一个导航任务从 `NavigateToPose` 发出到机器人产生控制输出，执行链到底如何运行
- `bt_navigator`、`planner_server`、`controller_server`、`behavior_server` 在运行时如何配合
- action、BT、lifecycle、server、plugin、costmap、localization、TF 如何互相咬合
- 配置、参数、插件装载、默认 BT、运行角色之间如何一一对应
- Nav2 为什么是这种架构设计，而不是另一种

一句话说清：

> 本模块要把“会跑、会测、会排障”提升成“能讲清执行链、能说清模块边界、能解释架构设计”。

本模块默认不是从零开始。

### 2.1 已经具备的基础

当前已经具备的基础包括：

- 闭卷问答、文档落盘、日志与结果归档意识
- Nav2 基线评估、最小 A/B 对照、跨地图泛化
- bag 回放链路
- failure case 整理
- 面向长期复盘的仓库化记录方式

### 2.2 当前能力已经达到的层次

当前已经不处于“不会跑 demo”的阶段，也不只是命令级入门阶段。

已经具备：

- 运行层经验
- 验证层经验
- 排障层经验
- 证据链沉淀意识

### 2.3 当前能力仍然缺的层次

当前仍然没有稳定进入以下层次：

- 执行链语言

也就是说，现在的问题不是“没做过”，而是“做过不少，但还没有被系统抽象成一张完整地图”。

## 3. 本模块要补的缺口

本模块要补的不是新的零散知识点，而是以下几类关键缺口。

### 3.1 运行现象和系统执行链之间的缺口

当前已经能看到很多运行现象，也能做一些排障，但还不能稳定把这些现象组织成一条完整主链：

- goal 由谁接收
- 流程由谁组织
- 规划由谁提供
- 控制由谁输出
- 支撑层在哪里介入
- 中间状态如何流转

### 3.2 模块名称和模块协作之间的缺口

当前可能已经知道：

- `bt_navigator`
- `planner_server`
- `controller_server`
- `behavior_server`

但仅仅分别知道它们是什么没有意义。

真正要补的是：

- 它们在同一个导航任务里的运行关系
- 谁是流程调度者
- 谁是能力提供者
- 谁处于 server 层
- 谁通过 plugin 提供具体实现
- 谁属于支撑层而不是主执行层

### 3.3 会改配置和知道“改到了哪一层”之间的缺口

当前已经接触过大量参数和配置，但还缺以下能力：

- 参数属于哪个模块
- 配置由哪个 node / server 读取
- 插件由哪个 server 装载
- 默认 BT 在流程里扮演什么角色
- 改动为何会造成对应的行为变化

### 3.4 概念理解和源码映射之间的缺口

当前还没有建立稳定的一层映射：

- 概念
- 包
- 节点
- 配置
- 运行时角色

如果没有这层映射，后续进入源码层就很容易散掉，看了一堆文件，脑子里还是一锅浆糊。

### 3.5 局部认知和架构解释之间的缺口

当前还很容易把 Nav2 解释成若干模块拼盘，而不能回答：

> Nav2 为什么要采用这种分层、这种协作关系、这种扩展方式，而不是另一种。

这正是本模块必须补上的最后一层。

## 4. 为什么现在学这个模块

本模块排在 01，不是为了形式上先学 Nav2，而是因为当前阶段最合理、最顺滑、最不跑偏的下一步，就是先完成 Nav2 的系统级重建。

### 4.1 为什么不是继续补基础命令

因为 ROS2 / Linux 基础命令训练、闭卷和证据链意识，已经在当前能力基线里具备。

当前瓶颈不在“命令不会敲”，而在：

- 执行链讲不清
- 模块协作讲不清
- 分层边界讲不清
- 配置挂载讲不清
- 架构设计讲不清

### 4.2 为什么不是直接跳去啃大量源码

因为如果没有执行链总图、边界表和支撑层耦合图，直接扎进源码，会很容易出现：

- 看了很多文件，但没有主干
- 记住几个类名，但讲不出系统在干什么
- 会说局部实现，但说不清它在整体里为什么存在

也就是说，会变成“看过一些代码”，而不是“真正进入系统核心层”。

### 4.3 为什么本模块是后续模块的入口

本模块结束后，能够为后续模块提供三类前置支撑：

- 为 `02_ros2_linux_fundamentals` 提供系统背景
- 为 `05_nav2_engineering_drills` 提供架构地图
- 为后续研究级评测、源码改造和论文工作提供模块边界与执行链基础

一句话说清：

> 现在先学 01，不是为了多学几个名词，而是为了先拿到一张后面多个模块都要反复引用的系统地图。

## 5. 模块总目标

本模块的总目标，是完成一次从运行层、验证层到系统层、架构层的认知升级。

### 5.1 执行链目标

能够从 `NavigateToPose` 发出开始，一路讲到机器人控制输出，并说明：

- 关键执行节点
- 状态流转
- 中间协作关系
- 支撑层的位置与作用

### 5.2 协作逻辑目标

能够说清：

- `bt_navigator`
- `planner_server`
- `controller_server`
- `behavior_server`

在运行时如何协作，而不是只会分别解释它们“各自是干什么的”。

### 5.3 分层边界目标

能够区分并说明以下对象所在层级、职责边界及相互咬合关系：

- action
- BT
- lifecycle
- server
- plugin
- costmap
- localization
- TF

### 5.4 配置映射目标

能够把以下对象建立清晰对应关系：

- 配置
- 参数
- 插件装载
- 默认 BT
- 运行角色

而不是停留在“会改配置但不知道改到了哪一层”。

### 5.5 结构映射目标

能够建立至少第一层结构理解：

- 概念 → 包 → 节点 → 配置 → 运行时角色

### 5.6 架构解释目标

能够回答：

> Nav2 为什么是这种架构设计，而不是另一种。

并且回答必须基于：

- 执行链
- 模块协作
- 系统分层
- 扩展点设计
- 配置与运行角色的分离关系

### 6.1 总学习日

本模块总时长为：

本模块共分为：

每个 Sprint 固定为 5 天，统一按以下节奏推进：

- Day 1：问题定义与图谱建立
- Day 2：运行时证据采集

## 7. 模块包含多少个 Sprint

本模块共包含 6 个 Sprint。

它们共同构成一条从“总执行链建立”到“模块级收口与总复盘”的递进路线。

这 6 个 Sprint 不是并列的知识点堆积，而是一条逐层深入的能力链：

- 先建立总链
- 再拆调度骨架
- 再钉职责边界
- 再纳入支撑层耦合
- 再打通配置、参数、插件与运行角色
- 最后进入源码入口整合与模块总收口

## 8. 每个 Sprint 的主题

### Sprint 1：从 goal 到 motion 的总执行链

核心任务：

- 建立从 `NavigateToPose` 到控制输出的总执行链
- 回答一条导航任务在系统里到底如何展开
- 形成后续 Sprint 反复引用的主链总图

### Sprint 2：BT、Action、Lifecycle 的调度骨架

核心任务：

- 说清流程是谁在调度
- 解释 action、BT、lifecycle 在任务发起、组织、状态管理中的位置
- 建立调度层与执行层的骨架理解

### Sprint 3：Planner / Controller / Behavior 的契约边界

核心任务：

- 说清三个核心 server 的职责边界
- 说明 server 与 plugin 的关系
- 建立核心模块职责与交互图

### Sprint 4：Costmap / Footprint / Localization / TF 的耦合关系

核心任务：

- 说明支撑层为何会共同影响导航行为
- 建立 costmap、footprint、TF、map、localization 的系统位置与影响链
- 完成支撑层耦合图

### Sprint 5：参数、插件、配置与架构内核

核心任务：

- 打通参数、配置、插件装载、默认 BT 与运行角色之间的对应关系
- 解决“会改配置但不知道改到了哪一层”的问题
- 完成第一版结构映射总表

### Sprint 6：源码入口整合与模块总复盘

核心任务：

- 回收前 5 个 Sprint 的图、表、问题与证据
- 建立概念到源码包的第一层清晰映射
- 完成模块总总结、总闭卷、证据索引与对 02 的衔接

## 12. 与下个模块的衔接关系

本模块不是终点，而是 `02_ros2_linux_fundamentals` 的前置系统地图。

### 12.1 本模块结束后已经拿到的东西

完成 01 模块后，应已经拿到：

- Nav2 执行链视角
- 模块协作视角
- 系统分层视角
- 配置挂载视角
- 概念到包 / 节点 / 配置 / 运行角色的第一层映射

也就是说，已经能回答“系统是怎么组织起来的”。

### 12.2 下个模块为什么成立

但 01 模块不会深挖到底的内容包括：

- ROS2 graph 为什么是观察系统和调试系统的入口
- topic / service / action 在运行时的差异到底是什么
- QoS 为什么足以改变系统行为与正确性
- DDS / RMW 在系统中扮演什么角色
- executor / callback group / spin / timer 为什么会影响开发上限
- lifecycle、time、TF、bag、launch、parameter 是如何形成系统级耦合的

这些问题需要由 02 模块继续解决。

### 12.3 模块衔接结论

一句话说清：

> 01 模块解决的是“Nav2 这套系统是怎么组织和协作起来的”，02 模块解决的是“ROS2 这套底层运行机制为什么会让系统表现成这样”。

没有 01，02 容易变成机制名词堆。
没有 02，01 的很多理解又会停留在半抽象、半经验层。

所以两者必须前后咬合。

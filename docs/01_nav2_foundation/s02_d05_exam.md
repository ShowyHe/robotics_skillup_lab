bt_navigator

## Q2
**题目：**  
为什么说 BT 属于“流程组织层”，而不是“能力执行层”？

**我的原始回答：**  
执行者是 planner、controller、behavior_server 还有 recovernode，bt_navigator 负责调度这些节点。

**GPT 修正后的标准回答：**  
BT 属于流程组织层，因为它决定的是：

- 先做什么
- 失败后切到什么
- 恢复后是否重回主线
- 恢复动作按什么顺序尝试

但 BT 本身不负责真正算路径、不负责真正算控制速度、不负责真正执行恢复动作。真正提供能力的是：

- `planner_server`
- `controller_server`
- `behavior_server`

其中 `RecoveryNode` 不是和这些 server 并列的一类能力实体，而是 BT 里的控制节点，用来组织失败后的恢复逻辑。  
一句话：**BT 负责流程组织，server 负责具体能力执行。**

## Q3
**题目：**  
`action` 在 Nav2 里解决的是什么问题？为什么不能把它等同于 BT？

**我的原始回答：**  
解决通信中给反馈给结果的问题，不能等同，因为 bt 是行为树，这个玩意相当于一个框架，整个导航怎么进行规划导航、恢复，已经在这里面定好了。

**GPT 修正后的标准回答：**  
`action` 解决的是长时任务的异步调用接口问题。它允许客户端向服务端发送 goal，并在执行过程中获得：

- feedback
- result
- cancel / abort 等状态

在 Nav2 里，`bt_navigator` 会通过 action 去调用其他能力节点，例如规划、路径跟踪、恢复动作等。

它不能等同于 BT，因为：

- **BT 解决的是流程组织问题**
- **action 解决的是跨节点任务调用与反馈问题**

一句话：**BT 决定“什么时候调谁”，action 提供“怎么把任务发给对方并收回结果”的机制。**

## Q4
**题目：**  
`lifecycle` 在 Nav2 中管的是什么？为什么它不等于任务调度？

**我的原始回答：**  
管的是 lifecycle nodes 状态，分为 unactive、unconfigured、active。

**GPT 修正后的标准回答：**  
`lifecycle` 管的是 lifecycle nodes 的状态管理，例如：

- `unconfigured`
- `inactive`
- `active`
- `finalized`

它解决的是：

- 节点何时初始化
- 何时激活
- 何时停用
- 系统启动和关闭时的有序管理

它不等于任务调度，因为：

- `lifecycle` 管的是**节点处于什么运行状态**
- BT / `bt_navigator` 管的是**当前导航任务流程走到哪一步**

一句话：**lifecycle 管“节点能不能干活”，BT 管“当前先让谁干活”。**

## Q5
**题目：**  
`bt_navigator`、`planner_server`、`controller_server`、`behavior_server` 四者的关系，最短怎么讲清？

**我的原始回答：**  
第一个是导航的管理者，决定什么时候做什么行为，第二个规划，第三个控制，第四个恢复。

**GPT 修正后的标准回答：**  
`bt_navigator` 是调度组织者，负责根据 BT 组织任务流程；  
`planner_server` 负责路径规划；  
`controller_server` 负责路径跟踪与速度控制；  
`behavior_server` 负责恢复或特殊行为动作，如 `spin / wait / backup`。

最短一句话：**bt_navigator 负责调度，planner/controller/behavior 三个 server 负责提供具体能力。**

## Q6
**题目：**  
什么叫“调度层”和“执行层”？Sprint 2 到底补的是哪一层？

**我的原始回答：**  
调度层是不参与执行，决定什么时候用什么节点执行导航任务，执行层是直接做具体导航任务，如规划、导航、恢复等等。补的是如果规划、导航失败，怎么恢复，恢复失败之后再怎么恢复，以及这些生命周期节点是怎么被管理的。

**GPT 修正后的标准回答：**  
**调度层**：决定任务流程如何组织，例如：

- 先规划还是先控制
- 失败后走局部恢复还是系统级恢复
- 恢复动作按什么顺序尝试

**执行层**：真正完成具体能力，例如：

- 计算路径
- 跟踪路径
- 执行恢复动作

Sprint 2 主要补的是**调度层骨架理解**，也就是把：

- BT
- action
- lifecycle

放到一张图里，讲清楚“导航任务到底由谁组织、怎么切步骤、怎么管理状态”。

不是只补“失败后怎么恢复”，那只是调度层里的一个子问题。

## Q7
**题目：**  
`ComputePathToPose` 和 `FollowPath` 在 BT 里分别对应什么角色？

**我的原始回答：**  
对应对 planner、controller 的调度。

**GPT 修正后的标准回答：**  
`ComputePathToPose` 和 `FollowPath` 在 BT 中都属于任务执行节点（BT action nodes）：

- `ComputePathToPose`：代表“向规划能力发起一次路径规划任务”
- `FollowPath`：代表“向控制能力发起一次路径跟踪任务”

更准确地说，它们是：

- BT 里的任务节点
- 对应 action 的 client 入口
- 分别把任务发给 `planner_server` 和 `controller_server`

所以不能只说“对应对 planner/controller 的调度”，还要补一句：  
**它们在 BT 里是流程节点，在系统里是对规划/控制能力的任务调用入口。**

## Q8
**题目：**  
局部恢复和系统级恢复有什么区别？

**我的原始回答：**  
局部恢复是规划或者导航失败后清图行为，系统恢复是局部恢复失败之后，进行旋转、退后、等待、清图等行为。

**GPT 修正后的标准回答：**  
**局部恢复**：发生在 `ComputePathToPose` 或 `FollowPath` 各自内部的 `RecoveryNode` 中，通常是某个具体步骤失败后先做一次就地补救，例如清对应 costmap。

**系统级恢复**：发生在外层 `NavigateRecovery` 的恢复子树中，当主线步骤反复失败后，系统会尝试更大的恢复动作，例如：

- clear
- spin
- wait
- backup

一句话：**局部恢复是“当前步骤先自救”，系统级恢复是“整条导航流程顶不住了再做更大动作”。**

## Q9
**题目：**  
为什么这几天做的 XML 修改实验，能说明“BT 改动会影响运行时行为”，但有些 case 不能证明外层 retry 结论？

**我的原始回答：**  
因为都是在局部恢复之后就成功了，还没进行系统恢复，也就不存在 retry。

**GPT 修正后的标准回答：**  
这几天的 XML 修改实验至少能说明：

- BT 文件内容可以被改动
- 运行时恢复行为确实会受 XML 结构和顺序影响

但有些 case 不能证明外层 retry 结论，原因是：

1. 有些目标只触发了局部恢复  
2. 还没稳定进入系统级恢复  
3. 更没有稳定耗尽外层 `NavigateRecovery` 的 retry 预算

所以这些 case 最多能说明：  
**恢复链存在、局部恢复生效、某些动作会被触发**

但不能严谨证明：  
**外层 `number_of_retries` 是否真的限制了系统级大恢复轮次。**

**我的原始回答：**

## Q12
**题目：**  
Sprint 2 学完后，为什么下一步必须进入 `Planner / Controller / Behavior` 的契约边界？

**我的原始回答：**  
这个时候就到了这些东西是怎么通信传递信息了，契约边界就是这些通信的钥匙，如果不符合就不能通信。

**GPT 修正后的标准回答：**  
Sprint 2 主要回答了“谁在调度”。  
下一步必须进入 `Planner / Controller / Behavior` 的契约边界，是因为如果只知道 BT 在调度，但不知道各 server：

- 接收什么输入
- 产出什么输出
- 失败时返回什么状态
- 各自职责截止到哪里

那整条导航链还是空的。

这里的“契约边界”指的是：

- 各模块的职责范围
- 模块之间通过什么接口衔接
- 请求、反馈、结果各自代表什么
- 哪一层负责组织，哪一层负责能力实现

一句话：**Sprint 2 解决“谁调度”，Sprint 3 要解决“被调度的这些能力模块，各自到底负责什么、怎么衔接、边界在哪”。**
